Manual/Gateway and connectivity

PORTABLE CONNECTIVITY

Connect Kitsu without an account or Heltec Wi-Fi.

The normal portable path uses the paired Android phone as Kitsu's bridge to the public gateway. The phone needs Bluetooth and Internet; the Heltec does not need a Wi-Fi network, username, or password.

Connect to the public gateway

You need the Android phone already paired and granted as a Kitsu controller, Bluetooth enabled, and working Internet on the phone.

  1. Open More in Android.

    The Public gateway card becomes available after at least one Kitsu is paired.

  2. Tap Connect to public gateway.

    Android creates a relay-only credential protected by Android Keystore and connects to Kitsu over authenticated Bluetooth.

  3. Hold PRG when Kitsu says GATEWAY / TO ENROLL.

    This locally authorizes the first-use device key. The server never receives a password or Wi-Fi passphrase.

  4. Wait for Connected to public gateway.

    Keep Bluetooth on and the phone near Kitsu. The phone may use cellular data or any Internet connection it already has.

No owner account is required.The gateway credential can carry traffic only for this phone installation and its enrolled Kitsu devices. Owner sign-in remains optional for separate owner-service features.
First enrollment uses trust on first use.A reflashable Heltec has no manufacturer account or factory attestation. The first accepted device key becomes the identity used to verify later traffic; PRG is the local physical authorization.

Optional direct Wi-Fi

Self-hosted and stay-at-home installations can still connect the Heltec itself to a network. For that separate path you need a 2.4 GHz Wi-Fi network using WPA2, mixed WPA2/WPA3, or WPA3 security.

Bluetooth controls setup commands without hiding the Wi-Fi link.While an authenticated Bluetooth session is active, Kitsu may keep its Wi-Fi station associated so the app can show whether the saved network works. Gateway enrollment, LAN commands, and remote actions remain stopped until Bluetooth closes, so there is never a second control path competing with the nearby session.

Configure Wi-Fi

  1. Connect to Kitsu over Bluetooth.

    The app must show Direct Bluetooth, not Remote. Owner sign-in is not required for this local step.

  2. Open Network and choose Wi-Fi setup.

    Enter the exact network name, select its security mode, and enter the passphrase.

  3. Submit once.

    The values are validated and sent only through the encrypted, authenticated device session. After a verified write, Kitsu reloads the live Wi-Fi driver from the encrypted record.

  4. Check storage and link separately.

    The app reports whether credentials were read-back verified independently from whether the radio is joining or connected. It clears the passphrase after an accepted write; it never stores the input on Android.

Optional self-hosted gateway

  1. Sign in to the owner account.

    Use the privately issued username and password. The app loads only gateway records belonging to that account.

  2. Select the available Kitsu gateway.

    The normal UI uses the signed catalog; manual certificates and pins remain an advanced recovery path.

  3. Save the gateway configuration.

    Routing details, server identity, certificate authority, and public-key pin are sent over the same authenticated Bluetooth session.

Enroll with the self-hosted gateway

  1. Tap Enroll for remote access.

    The backend creates a one-use, short-lived claim bound to the selected gateway and companion.

  2. Wait for Kitsu to show GATEWAY / TO ENROLL.

    Physically inspect the device before approving.

  3. Hold PRG within the confirmation window.

    This is the third physical approval in a full first-time setup: two for the phone, one for remote enrollment.

  4. Let the app finish the Bluetooth handoff.

    The device creates its own enrollment key material, the app sends the finish request, and Bluetooth closes intentionally. Only then may Kitsu use the already-associated Wi-Fi link for gateway bootstrap.

  5. Wait for authenticated remote connection.

    Kitsu obtains trusted time, completes bootstrap and mutual TLS, and uploads a signed snapshot. The app must see that fresh device-authenticated snapshot before it reports completion.

Enrollment becomes committed after the PRG hold.Before that point, Stop setup disconnects Bluetooth and clears the staged claim. After the physical approval, closing the app only stops waiting; it does not pretend to revoke work already approved on the device.

Connection states

StateWhat to do
Credentials not storedAdd Wi-Fi over Direct Bluetooth.
Wi-Fi connected, gateway not configuredSign in, choose an owner-scoped gateway, and store its trust record.
Enrollment pendingComplete the app flow and hold PRG when Kitsu asks.
Bluetooth activeThe Wi-Fi station may remain associated, but gateway bootstrap and remote traffic wait for the nearby session to close.
Time pendingLeave the network connected. Kitsu obtains trusted time before opening TLS.
ConnectingWait through the bounded retry. The local UI and MeshCore receiver remain responsive.
ConnectedRemote state and actions can use fresh authenticated device snapshots.
BackoffThe last attempt failed. Kitsu retries with increasing delay; check the 2.4 GHz network, security selection, passphrase, and gateway availability.

Change or remove the network

Reconnect over Bluetooth and submit the new Wi-Fi configuration. A successful replacement rotates the encrypted record, verifies its read-back, and reloads the live Wi-Fi driver. Disconnecting the phone does not erase Wi-Fi.

Firmware 0.10.2 has no Wi-Fi-only erase command or supported public factory-reset flow.Replacing the saved network is supported. A full-chip erase also destroys the device identity and companion pack, so do not use one for Wi-Fi troubleshooting. For decommissioning, retain a complete recovery backup and use only an explicitly documented destructive recovery procedure.
