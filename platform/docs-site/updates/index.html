Manual/Firmware updates

SIGNED A/B BLUETOOTH UPDATE

Update nearby; recover over USB.

After the initial USB installation, normal Kitsu updates can be transferred from Android over the existing authenticated Bluetooth connection. The device verifies the release itself, writes only the inactive application slot, and uses bootloader rollback if the new image cannot stay healthy.

Release availabilityThe public installer and download surface fail closed while a firmware candidate is still in physical acceptance. If no signed release is offered, wait; do not substitute an unaccepted local candidate.

Normal Bluetooth update

  1. Download the signed .kitsu-fw file.

    Use the Kitsu release page in your browser and save the exact package. It contains one canonical signed manifest, one raw signature, and one ESP32-S3 application image.

  2. Connect the target Kitsu in Android.

    The update operations are allowed only after the normal controller-authenticated Bluetooth handshake.

  3. Choose the package in Settings.

    The app checks the container boundaries, manifest schema and order, Kitsu update-authority signature, target device class, image layout, size, checksum, appended hash, and SHA-256.

  4. Tap Install on selected Kitsu.

    The Heltec independently repeats the signature, target, and image checks before it erases or writes the inactive slot. Chunks are written sequentially, read back, and checkpointed.

  5. Keep Kitsu powered and nearby.

    A GATT interruption resumes from the device's reported offset. A power interruption resumes from the last durable 64 KiB checkpoint and never changes the running slot prematurely.

  6. Wait for reboot and confirmation.

    Finish verifies the streaming and full flash hashes plus ESP image structure before selecting the new slot. The new firmware must complete critical initialization and stay healthy for 30 seconds before it becomes permanent.

If the connection drops

Reconnect the same saved Kitsu and choose the same package. Android asks the device for authoritative status before sending another chunk. A lost write receipt is not treated as permission to blindly duplicate data; the device either confirms an already-written byte range or reports the exact next offset.

A recoverable disconnect resumes automatically. If the app reports a terminal failure, use Reset interrupted update. It aborts only the inactive update state and verifies that the device returns to Idle before another install.

Automatic rollback

On the first boot of a new slot, Kitsu leaves the ESP-IDF rollback flag pending. Legacy-connectivity retirement, device security, saved controller storage, BLE advertising, OTA image/journal binding, and the main loop must initialize successfully and remain healthy for 30 continuous seconds. A crash, watchdog reset, power cut, invalid image journal, retired-storage failure, or explicit critical-init failure before confirmation returns the board to the previous slot.

USB bootstrap and recovery

Use the Web Serial installer for the first A/B-capable Kitsu install or when Bluetooth OTA cannot be reached. The signed manifest and versioned physical-acceptance record bind the exact SHA-256 of the reviewed rollback-enabled bootloader, partition table, application, one clean 4 KiB OTA-journal artifact, and one 256 KiB legacy-connectivity clear artifact. The manifest binds the journal artifact to 0x33f000 and 0x66f000, and binds the connectivity clear to the isolated retired region at 0x7b0000. The installer writes the accepted application to both A/B slots and reads back all seven regions. Unlike normal Bluetooth OTA, this USB bootstrap intentionally writes the bootloader and partition table and removes historical Wi-Fi, gateway, device-certificate, and server secrets. It never performs a full-chip erase or writes OTA selection data, companion state or packs, controller records, MeshCore state, coredump, or eFuses. Close serial monitors first and use a stable USB data cable.

Never full-erase for a routine update.A whole-chip erase destroys companion state, visual packs, controller authorization, MeshCore configuration, and recovery data. The supported Bluetooth and USB paths do not require it.
