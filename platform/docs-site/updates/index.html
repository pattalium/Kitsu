Manual/Firmware updates

SIGNED A/B BLUETOOTH UPDATE

Update a migrated Kitsu nearby.

Once Kitsu runs the accepted 0.20.3 current layout, normal updates transfer from Android over the existing authenticated Bluetooth connection. The device verifies the release itself, writes only the inactive application slot, and uses bootloader rollback if the new image cannot stay healthy.

Release and layout availabilityThe public firmware card fails closed while a candidate is still in physical acceptance. If it offers no signed .kitsu-fw, wait; do not substitute an unaccepted local candidate. A .kitsu-fw is application-only and cannot migrate a 0.20.2 legacy partition layout.

Normal Bluetooth update

  1. Download the signed .kitsu-fw file.

    Use the Kitsu firmware card and save the exact package only after its same-origin route, byte count, SHA-256, canonical manifest, and embedded signature verify. It contains one canonical signed manifest, one raw signature, and one ESP32-S3 application image.

  2. Connect the target Kitsu in Android.

    The update operations are allowed only after the normal controller-authenticated Bluetooth handshake and a current-layout status check.

  3. Choose the package in Settings.

    The app checks the container boundaries, manifest schema and order, Kitsu update-authority signature, target device class, ESP image, exact firmware identity marker, current layout geometry, size, checksum, appended hash, and SHA-256.

  4. Tap Install on selected Kitsu.

    The Heltec independently repeats the signature, target, layout, and image checks before it erases or writes the inactive slot. Chunks are written sequentially, read back, and checkpointed.

  5. Keep Kitsu powered and nearby.

    A GATT interruption resumes from the device's reported offset. A power interruption resumes from the last durable 64 KiB checkpoint and never changes the running slot prematurely.

  6. Wait for reboot and confirmation.

    Finish verifies the streaming and full flash hashes plus ESP image structure before selecting the new slot. The new firmware must complete critical initialization and stay healthy for 30 seconds before it becomes permanent.

If the connection drops

Reconnect the same saved Kitsu and choose the same package. Android asks the device for authoritative status before sending another chunk. A lost write receipt is not treated as permission to blindly duplicate data; the device either confirms an already-written byte range or reports the exact next offset.

A recoverable disconnect resumes automatically. If the app reports a terminal failure, use Reset interrupted update. It aborts only the inactive update state and verifies that the device returns to Idle before another install.

Automatic rollback

On the first boot of a new slot, Kitsu leaves the ESP-IDF rollback flag pending. Legacy-connectivity retirement, device security, saved controller storage, BLE advertising, OTA image/journal binding, and the main loop must initialize successfully and remain healthy for 30 continuous seconds. A crash, watchdog reset, power cut, invalid image journal, retired-storage failure, or explicit critical-init failure before confirmation returns the board to the previous slot.

One-time 0.20.2 to 0.20.3 transition

A legacy-layout 0.20.2 board cannot be moved to the current layout by Bluetooth OTA, ordinary PlatformIO upload, generic Web Serial, or a whole-chip erase. The transition is a private, physically supervised service ceremony. It is not an owner download and its commands, backup locations, and raw evidence are not published.

  1. Capture two independent recovery authorities.

    The complete 8 MiB flash is read and verified twice into owner-only directories on different physical volumes. The device remains in the ROM loader; it is not rebooted between capture, audit, and migration.

  2. Prove the expanded NVS is readable without mutation.

    The captured 20 KiB NVS prefix is extended with 59 erased pages to form the 256 KiB candidate. A fresh oracle compiles and runs the real pinned IDF 4.4.7 storage implementation twice and must enumerate critical state with zero writes and zero erases.

  3. Stage the current applications before the table.

    The reviewed image, relocated OTA data, expanded NVS, blank journals, and erased gaps are written and read back while the accepted legacy table remains in place. Companion packs and other upper storage are preserved through the pre-reset readback.

  4. Commit the current table last.

    The current partition-table sector is the final flash mutation. The complete 8 MiB result is read back and durably recorded before the sole reset.

  5. Keep restore table-last too.

    Dedicated restore starts only from one of the original frozen backups, invalidates the table first, restores and verifies non-table bytes, writes the accepted legacy table last, and then resets. A capture made during a failed transition is never a new recovery authority.

Historical pre-0.20.3 onlyThe already-published seven-write Web Serial bundle remains immutable authority for its accepted legacy layout. It targets legacy slots and writes the table too early, so it must never install, migrate, repair, or recover firmware 0.20.3 or a board with an unknown layout.

When a migrated board cannot boot

Do not force the historical flasher, generic PlatformIO targets, or a filesystem upload. The dedicated private restore ceremony uses the original double backups and exact migration record. If Kitsu still boots and authenticates over Bluetooth, use only the signed .kitsu-fw path above; if it cannot, stop and arrange the supervised restore rather than rewriting raw regions.

Never full-erase for a routine update.A whole-chip erase destroys companion state, visual packs, controller authorization, MeshCore configuration, and recovery data. Neither signed Bluetooth OTA nor the dedicated private migration/restore ceremony requires it.
