Historical-layout USB recovery

Recover a legacy Kitsu safely.

This installer is only for a Heltec that still has the exact reviewed pre-0.20.3 partition layout. It reads and hashes the physical partition table before enabling installation and again before the first write. A board already migrated to the 256 KiB NVS layout is blocked here and uses Android's signed .kitsu-fw updater instead. Pet replacement remains a separate, explicit destructive choice.

Device

Write and read back

Legacy layout only. Install unlocks only for an ESP32-S3 with 8 MiB flash and the exact historical partition-table hash. On that approved source layout, the recovery performs seven verified core writes: the rollback-enabled Kitsu bootloader, partition table, the same accepted app in app0 and app1, a clean private OTA journal in each slot, and one exact clear over the isolated retired connectivity partition. Keep current pet is forced on every page load. If you explicitly choose a different species, a PREPARED record preserving the original pet identity is verified before any pack byte; a separate matching COMMITTED record is verified only after exact pack readback. Interrupted replacements resume only with that bound target and preserve both transaction sectors while re-clearing the retired suffix. One final reset boots the complete result; no intermediate starter is booted.

Keep current pet is the safe default. The companion-pack slot and pet progress will not be written. Choosing a different species requires a separate destructive confirmation.

Owner-reflashable by design. This historical recovery installer writes the reviewed legacy-layout Kitsu bootloader so its Bluetooth updates can roll back safely and clears only the retired partition that held legacy Wi-Fi, gateway, and server credentials. It never calls full-chip erase and never writes OTA data, controller records, MeshCore state, coredump, or eFuses. The companion slot stays byte-for-byte untouched in the default mode. A different species requires two explicit confirmations plus separate PREPARED-before-pack and COMMITTED-after-readback records. A pending replacement cannot be silently discarded when its physical source pack is no longer intact. The 0.20.3 storage transition is a separate private table-last ceremony; after migration, use signed Android Bluetooth OTA or the dedicated restore procedure, never these legacy offsets.
